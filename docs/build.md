## 2. Locked decisions

### 2.1 Stack

| Area | Decision |

### 2.5 CORS

### 2.6 Auth and the portal

- Portal login checks `portal_users` (direct `SELECT` of the password hash with the public pool) and bcrypt-verifies it. On success it sets the cookie `auth=ok; HttpOnly; SameSite=Strict; Secure; Path=/; Max-Age=86400` and redirects 302 to `/`.
- The cookie stays the plain unsigned string `ok`. Signing it is a later improvement (section 9). This is a known weakness: anyone who sends `Cookie: auth=ok` passes the portal gate. It protects portal pages and docs only. API routes enforce their own headers and tokens.
- `Secure` is always on. A browser only sends a `Secure` cookie over HTTPS or `http://localhost`, so portal login over plain HTTP on any other address will not stick.
- API login checks `api_users` (`user_name`, `password_hash`, `user_role`) and issues a JWT: `sub` is the user name, `role` is the user role (`admin` or `user`), 1 day expiry, issuer `kafka-api-gateway`.
- An expired token returns 401 `EXPIRED_TOKEN`. Any other bad token (bad signature, wrong issuer, malformed) returns 401 `INVALID_TOKEN`, and a token without `sub` or `role` returns 401 `MISSING_SUB_OR_ROLE`. The old code mapped every failure to `INVALID_TOKEN` (D25).
- API key check: call `fn_verify_api_key` with the key, then bcrypt-verify the secret against the returned hash. In the old code the failure is saved on the request, not thrown, and each route decides what to do with it.
- Client headers: a wrong value returns 400 `INVALID_HEADER_VALUES` (not 401). Missing returns 401 `MISSING_AUTH_HEADERS`. Keep both.

### 2.7 Global gate order (old behavior to replicate)

1. WebSocket upgrades and the exact path `/api/v1/ws-subscribe` pass without the gate. The route itself authenticates.
2. Valid `x-client-id` and `x-client-secret` pass, but only for requests whose `Accept` does not include `text/html`.
3. `/login*` passes.
4. Cookie `auth=ok` passes.
5. Any path with a file extension passes.
6. Paths under `/api/` pass when the request does not send `Accept: text/html`. The route then returns its own JSON 401 or 400 (D23).
7. Everything else gets a 302 redirect to `/login`.

In Rust the gate is a `route_layer`, so it only wraps routes that exist (see D13).

## 4. Behavior of the old gateway to replicate

### 4.1 Startup order

1. Validate env (fatal on failure).
2. Create the service DB pool. The default pool stays lazy.
3. Load the topic registry and validate that the consume topics exist in Kafka (fatal on failure), then start the bridge consumer.
4. Only then start listening on `0.0.0.0:APP_PORT`.

### 4.2 Health

- `/api/v1/health{,/app,/db}`: require client headers. DB down returns 503 `DB_PROBE_FAILED`.
- `/healthz{,/app,/db}`: portal pages or JSON by `Accept`. They return 200 even when the DB is down, with the DB status inside the body. Keep this.

### 4.3 Producer

Connects at boot (D29) and is reused. Messages carry a key and optional headers. The reply carries the partition and offset. Acks all: `with_acks(-1)` plus `with_enable_idempotence(true)`. `max_request_size` is 11 MiB for the 10 MB message limit.

### 4.4 Consumer bridge

Old consumer settings: `groupId` from `KAFKA_GROUP_ID`, session timeout 60 s, heartbeat 3 s, auto commit off, auto resolve off, and `fromBeginning` not set. A new group with no committed offsets therefore starts at the latest offset.

For each Kafka record:

1. Parse the value as JSON and validate `{correlationId: UUIDv7, ...anything}`. Empty, malformed or invalid values are logged and committed (skipped).
2. Read the topic policy from the registry.
3. Topic with `ack_required`:
   - Pick the owner: the subscribed session with the lowest subscriber ID.
   - If nobody is subscribed, poll every 500 ms until someone is, or until the consumer stops.
   - Send the event to every subscriber of the topic. Only the owner's ACK is awaited.
   - Wait up to 5 minutes for the owner's `processed` frame.
   - On ACK, commit `offset + 1` `[VERIFY]` and move on.
   - On timeout or when the owner disconnects, fail the wait. Nothing is committed and the same message is redelivered. This is at-least-once delivery.
4. Topic without `ack_required`: send to all current subscribers and commit immediately. With no subscribers the message is dropped and committed.

Event frame sent to subscribers: `{type:"event", topic, partition, offset (string), headers:{...}, ...payload}`.

### 4.5 `/api/v1/ws-subscribe`

Auth happens when the connection opens. On failure the server sends `{type:"error", ...authError}` and closes with code 4001. On success it sends `{type:"ready"}`.

Client to server:
- `{type:"subscribe", topic}` and `{type:"unsubscribe", topic}`
- `{type:"processed", correlationId}` (UUIDv7)
- `{type:"publish", requestId (uuid), topic, key?, value (object), headers? (string map)}`

Server to client:
- `{type:"subscribed", topic}` and `{type:"unsubscribed", topic}`
- `{type:"published", requestId, topic, partition, offset}`
- `{type:"ack-received", correlationId}`
- `{type:"error", message, reason?}` with messages `Invalid message format` (plus `issues`), `Malformed JSON`, `ACK rejected`, and the publish failure reason.

A subscriber can publish only to topics marked `subscriber_publish_allowed`. A subscribe request is not checked against the registry. A topic nobody consumes simply never delivers.

### 4.6 `/api/v1/ws-publish`

This route is different from `ws-subscribe` and is job-style. On open the server sends `{type:"ready", message:"WebSocket publish connection established"}`. The client sends `{topic (min 1), jobName (min 1)}`. The gateway publishes `{correlationId, apiUserId, jobName, timestamp (ISO)}` with the API key as the Kafka key, then replies `{type:"ack", topic, correlationId}`. This `ack` means published, not processed. Error frames are `{type:"error", message}`. D5, D6, D14 and D15 apply here.

### 4.7 Graceful shutdown `[DECIDED]`

On `SIGTERM` or Ctrl-C, in this order:
1. Stop accepting new connections.
2. Tell the bridge to stop, using a `tokio::sync::watch` flag (no extra crate).
3. Close every WebSocket session with code 1001 (going away). Pending ACK waits fail, so nothing is committed.
4. Stop the consumer loop and call the consumer's `shutdown()`.
5. Flush the producer.
6. Close the DB pools and exit.

Hard time limit: 8 s from the signal `[DECIDED]` (D36). A watchdog logs an error and exits with code 1 if the shutdown is still running after that.

## 8. `kafkit-client` 0.1.9

Read from the crate source (2026-10-30). Not compiled or run.

API surface found:
- Consumer: `subscribe(Vec<String>)`, `unsubscribe()`, `poll()`, `poll_for(Duration)`, `commit(&records)`, `commit_offsets(Vec<CommitOffset{topic, partition, offset}>)`, `pause` and `resume` (`Vec<TopicPartition>`), `seek`, `assignment()`, `committed()`, `shutdown(self)`.
- Producer: `connect(config)`, `send(KafkaMessage)` returning `ProduceAck{topic, partition, base_offset, offset, ...}`, `flush()`. Headers are supported.
- `enable_auto_commit` defaults to false. Heartbeats are scheduled by the consumer's own runtime loop, not by `poll()` calls, so the manual heartbeat of the old ACK wait is not needed.
- It is a poll loop, not kafkajs's `eachBatch` callback. There is no `isStale` or `resolveOffset`. A failed record is retried by seeking back to its offset.

Differences from the old client that must be handled:
- `auto_offset_reset` defaults to earliest. The old consumer effectively used latest. Set latest, otherwise a new group would replay the whole topic.
- Producer `max_request_size` defaults to 1 MiB. Raise it for the 10 MB limit.
- `fetch_max_bytes` defaults to 50 MiB, which is enough. `partition_max_bytes` defaults to 1 MiB and is set to 11 MiB in the consumer. `[DONE]` A 9 MB message was consumed through the bridge on 2026-11-03.

Spike results (2026-11-01, run against the local apache/kafka:4.1.0 broker with a throwaway spike (removed in Phase 4, see commit b243e5d)):
1. `[DONE]` `subscribe` replaces the subscription. The full topic list is passed each time.
2. `[DONE]` `subscribe` with a smaller list drops the removed topic cleanly. The later topic-removal feature is possible.
3. `[DONE]` `KafkaAdmin::list_topics()` for the startup check. `KafkaConsumer::list_topics()` also exists.
4. `[DONE]` `commit_offsets` expects `offset + 1`. Committing 10+1 made the broker report 11.
5. `[DONE]` `seek` back on one partition replays it while other partitions keep flowing. `pause` and `resume` work.
6. `[DONE]` `with_acks(-1)` plus `with_enable_idempotence(true)`.
7. `[DONE]` Consuming records above 1 MB. A 2 MiB send was rejected with `MessageTooLarge` because the broker limit is still 1 MB. Retest after the user raises the broker and topic limits.

Broker side (done by the user, not by the gateway): to carry messages above 1 MB, raise the broker `message.max.bytes` and the topic `max.message.bytes`. Check the replica fetch limit too. Kafka does not reserve memory for the limit. It is only a ceiling.
